# Карта логики: lean-spec

Как один запрос пользователя («проверь через lean», «ускорь, но докажи», «проверь шаг 18 карты логики») становится
моделью на Lean, доказанными теоремами, дифф-тестами и зелёным гейтом в репо пользователя.
Карта описывает скилл как он есть сегодня, по шагам: что решает агент, где поток ветвится и какой файл скилла это ведёт.

Пути в строках `Module:` идут от `plugins/lean-spec/skills/lean-spec/`, без расширения.
Номера шагов - номера карты; в заголовке шага указан раздел SKILL.md (§), из которого он взят. `references/map-mode.md` пользуется номерами §.
Известные пробелы и правки - в `docs/logic-map-fixes.md`; план развития плагина - `PLAN.md`.

Правило: правишь шаг или ветку скилла - правь `logic-map.md` и этот файл в том же коммите.
`tests/test_lean_spec.py` (корень репо) проверяет, что каждая строка `Module:` указывает на настоящий файл или папку.
Это зеркало; главный файл - `docs/logic-map.md`.

## Поток коротко

```
запрос пользователя + репо
  │
  ├─ 0  Предпроверка .......... есть ли lake и bwrap; какой Lean; есть ли уже lean/
  ├─ 1  Цель и шаблон ......... какая функция или шаг карты; A, E, S или C; режим карты или нет
  ├─ 2  Копия шаблона ......... lean/ и tests/ из example/, Frozen сброшен
  ├─ 3  Модель ................ эталон на Lean (по требованию, а для S - переходы кода)
  ├─ 4  Формулировки .......... какие теоремы; молчаливые выборы и ложные утверждения помечены
  ├─ 5  Утверждение ........... пользователь утверждает формулировки или утвердил заранее
  ├─ 6  Заморозка ............. Frozen.lean + comparator.json, пока доказательства - sorry
  ├─ 7  Доказательства ........ по одной sorry; ложная формулировка останавливает прогон
  ├─ 8  Оракул ................ lake exe oracle отвечает замороженным эталоном, строка за строкой
  ├─ 9  Дифф-тесты ............ Hypothesis: прод-код == оракул на целых значениях
  ├─ 10 Известные находки ..... расхождения закреплены strict xfail, маски узкие
  ├─ 11 Проверка мутациями .... ≥3 поломки прод-кода должны уронить тест
  ├─ 12 Быстрый путь и замер .. (только E) код повторяет fast/checkInv; цифры до и после
  ├─ 13 Гейт .................. lake build, grep обходов, lake comparator, тесты
  ├─ 14 Отчёт ................. Доказано / Только проверено, проверка во время работы, находки
  └─ 15 Запись в карту ........ (только режим карты) строка Proved:, тест карты, план находок
  │
lean/ + тесты в репо пользователя, отчёт, в режиме карты - изменённая карта логики
```

Скилл не трогает прод-код, пока шаг 9 не прошёл без масок, а в режиме карты не трогает вовсе, если не попросили.

## Где поток делится по шаблону

Шаблон выбирает агент на шаге 1 по словам пользователя и по коду; сам скилл его не вычисляет.

| Шаблон | Что включает | Какие шаги меняет | Что меняется |
|---|---|---|---|
| A: модель + дифф-тесты | по умолчанию | 3, 4, 9, 11 | модель по требованию; тесты сравнивают код и модель |
| E с инвариантом данных | быстрый путь рядом с медленным, верный только на части данных | 3, 4, 8, 9, 11, 12 | пара `spec`/`fast`, оракул зовёт только `spec`; `fast_eq_spec : Inv → …`, `checkInv_sound`; проверка во время работы с откатом; две стратегии (любой вход, вход с инвариантом) |
| E со свойством правила | условие быстрого пути - свойство предиката (совпадения делят ключ) | 4, 12 | гипотеза о предикате; без проверки во время работы; тест свойства вместо неё |
| E без гипотезы | ключ корзины входит в само условие совпадения | 4, 12 | `fast = spec` для всех входов; ни проверки, ни теста свойства |
| S: автомат со сбоями | цикл, который реагирует на сбои: повторы, переход на другой провайдер, переподключения | 3, 4, 7, 9, 10, 11, 14 | модель = функция переходов кода над конечным списком событий; ложные утверждения как `¬ Claim`; заглушки по сценарию; стратегии цепочек событий |
| C: ёмкость и лимиты | ограничитель частоты, квота, очередь или предел, чьи цифры важны | 3, 4, 9, 11, 14 | модель = переходы кода, время - данные; границы счёта как `def Claim`; сбои - слагаемым в границе; управляемые часы, нагрузочный тест; таблица ёмкости |
| Режим карты | в репо есть `docs/logic-map.md`, пользователь называет шаг или просит сверить карту | 1, 3, 4, 9, 10, 14, 15 | строки шага - требование; цитаты `-- map:`; находки в план карты; код не меняется |

Примеры:
- «ускорь `normalize`, но докажи» → E; какой E - зависит от того, нужен ли быстрому пути инвариант данных.
- «докажи, что цикл повторов не выбирает провайдера дважды» → S.
- «сколько попыток пароля пропустит ограничитель входа за сутки» → C.
- «проверь через lean шаг 18 карты логики» → режим карты с A.

Module: `SKILL`, `references/patterns`, `references/map-mode`

## Точки входа

## Шаги

### 0. Предпроверка (§0)

Решает: можно ли начинать и что поставить.
Вход: корень репо. Выход: факты `имя: значение`, строки `install …`.
Ветки:
- macOS → код 1 с причиной, не поддерживается (#4);
- нет lake или bwrap → код 1; скилл показывает строки установки и останавливается;
- lake только в `~/.elan/bin` → каждая следующая команда шелла начинается с `export PATH="$HOME/.elan/bin:$PATH"`;
- версия Lean ≠ 4.35.0 → предупреждение «API drift is likely», прогон идёт дальше;
- нет lean-lsp-mcp → предлагается перед доказательствами (шаг 7); нет lean4-skills → необязательно;
- `lean_project: lean/ (exists …)` → шаг 2 добавляет цель рядом с замороженной, а не копирует шаблон.
Сбой: падение `lean --version` → `unknown (…)`, прогон идёт дальше.
Module: `scripts/preflight`, `SKILL`, `references/setup`

### 1. Цель и шаблон (§1)

Решает: одну цель, её шаблон (A, E, S, C) и включён ли режим карты.
Ветки:
- пользователь назвал область, а не функцию → 2-4 кандидата по пользе и усилиям, первой - с наибольшей пользой
  на единицу усилий (80/20), остальные - в отчёт как следующие цели;
- есть `docs/logic-map.md` и пользователь называет шаг → режим карты; цель = `Module:` шага; только шаги, которые
  решают по данным в памяти;
- модель больше ~200 строк → отказ или разбиение;
- сам IO (сеть, драйвер БД) → отказ; логика, которая реагирует на IO (повторы, переходы, переподключения) → S с
  подменой IO;
- E → сначала замер одного реального запроса целиком (куда уходит время), потом цифры «до» для самой цели.
Module: `SKILL`, `references/patterns`, `references/map-mode`

### 2. Копия шаблона (§2)

Решает: раскладку `lean/` и тестового файла в репо пользователя.
Выход: `lean/` (lakefile, toolchain v4.35.0, гейт, оракул, comparator.json), `tests/test_spec_oracle.py`, иногда
`tests/conftest.py`; в `.gitignore` добавляются `lean/.lake/` и `.hypothesis/`; `Spec/Feed/` удалён; `Frozen.lean`
сброшен до шапки; `lean/Spec.lean` импортирует цель вместо Feed; `Oracle.lean` импортирует модель цели, а `answer`
до шага 8 отвечает заглушкой `error: no oracle yet`; в `comparator.json` нет имён теорем.
Ветки:
- `lean/` уже есть → сначала прогнать существующий гейт, он должен быть зелёным; без копии, `Frozen.lean` не
  сбрасывается: новая `lean/Spec/<Target>/`, импорт в `Spec.lean`, ветка оракула с тегом (тег разбирается до старого
  разбора), тестовый файл в `TEST_CMD`, если тот перечисляет файлы, все проверки примера переносятся в старый
  `gate.sh` (его `TEST_CMD` остаётся), после заморозки прежний блок Frozen сверяется diff'ом;
- тесты репо не импортируют модули из корня → копируется и `conftest.py`.
Module: `SKILL`, `example/lean`, `example/tests`

### 3. Модель (§2)

Решает: что считается эталоном.
Выход: `lean/Spec/<Target>/Model.lean` на `List` и `Nat`, без оптимизаций; для E - `spec`/`fast`.
Ветки:
- A, E: пишется по требованию (строки карты, docstring, задача), не по телу кода;
- требование молчит (ничьи, округление, что максимизируется) → выбор кода, отдельная строка `-- silent:`
  (внутри `/-- -/` ломает лексер), находка;
- код на SQL → NULL как `Option` с позицией сортировки движка; равные ключи - устойчивая сортировка по порядку
  входа; нет последнего ключа - находка, когда `LIMIT` решает, кого выбрать;
- код читает внешний формат (дифф git, CSV, кадр протокола) → вход моделируется по грамматике формата, а не по
  ожиданиям кода (greenkeep: четыре бага);
- E со свойством правила: `spec` - существующий алгоритм, большая часть модели - `-- silent:`;
- S: функция переходов самого кода; окружение - один конечный список событий, рекурсия структурная;
- C: то же, время - число в событии, хранилище (ключи, счётчики, очередь) - значение; чередование реплик - отдельная
  модель на уровне операций.
Module: `SKILL`, `references/patterns`

### 4. Формулировки (§2)

Решает: что будет доказано.
Выход: `Props.lean` со всеми теоремами и `sorry`; зелёный `lake build` только с предупреждениями о `sorry`.
Ветки:
- E: `fast_eq_spec` (с `Inv`, с гипотезой о предикате или без) и `checkInv_sound`, если есть проверка;
- режим карты: одна теорема на строку правила с цитатой `-- map: "…"`; `Decides:` теоремы не получает;
- S: свойства безопасности (конечное число шагов, без повторов, одна запись) и обещания документации; ложное
  становится `def Claim : Prop` + `theorem claim_false : ¬ Claim` с конкретным примером;
- C: границы счёта (за окно, за любые W секунд, за сутки, без вечной блокировки), каждая сначала как `def Claim`;
  сбои - слагаемым в границе; реальные настройки - следствия через `decide`.
Module: `SKILL`, `references/map-mode`, `references/patterns`

### 5. Утверждение (§2)

Решает: говорят ли формулировки то, что имеет в виду пользователь.
Ветки:
- по умолчанию → модель и каждая формулировка простыми словами, потом ждать;
- утверждено заранее → без остановки; отчёт перечисляет их простыми словами.
Module: `SKILL`

### 6. Заморозка (§2)

Решает: с чем `lake comparator` сверяет доказательства.
Выход: `Frozen.lean` += модель и формулировки без импортов `Spec` (блок на цель), импорты библиотек (Mathlib, Std)
подняты в начало файла; `comparator.json` перечисляет имена
теорем; только стандартные аксиомы.
Ветки:
- перед заморозкой: `#eval` модели на двух-трёх входах, написанных руками; сниппет заморозки - с абсолютными путями;
- вторая цель → её блок дописывается, её имена добавляются; блок первой цели не трогается;
- функцию, которую зовёт оракул, не упоминает ни одна теорема из списка → до заморозки добавляется теорема о ней;
- вспомогательные леммы, добавленные позже, в Frozen не идут и утверждениями не считаются; формулировки и Frozen меняются только с согласия и вместе.
Module: `SKILL`, `example/lean/Frozen`, `example/lean/comparator`

### 7. Доказательства (§3)

Решает: верна ли каждая замороженная формулировка для модели.
Ветки:
- стоит lean4-skills → `/lean4:prove` на каждую `sorry`; иначе цикл доказательства (сначала цель, автоматика, поиск, `#check`);
- появился контрпример → формулировка ложна: остановиться и показать (находка о требовании);
- ~5 попыток на одну цель без успеха → вспомогательная лемма или пересмотр определения;
- S: контрпример - баг кода (или документации): показать, затем эта формулировка переворачивается в `¬ Claim` в
  Props и Frozen вместе и доказывается примером; при утверждении заранее без вопроса, иначе с вопросом.
Сбой: в A и E баги «код против требования» здесь не видны (модель следует требованию), их находит шаг 9; в S
находки приходят из теорем.
Module: `SKILL`, `references/proof-loop`

### 8. Оракул (§4)

Решает: как тесты добираются до замороженного эталона.
Вход: одна строка натуральных чисел через пробел. Выход: весь результат эталона или `error: …`.
Ветки:
- несколько целей или несколько функций одной цели → тег в начале строки, разбор в `answer`;
- текстовый вход → `List Char` в модели; строка передаётся длиной, затем кодами символов;
- предикат, который считает код → передаётся данными (матрица n×n из 0/1).
Сбой: конец ввода → цикл завершается; кривая строка → `error: …`, `int()` в тесте падает.
Module: `SKILL`, `example/lean/Oracle`

### 9. Дифф-тесты (§5)

Решает: совпадает ли прод-код с моделью.
Вход: данные Hypothesis. Выход: успех или ужатый контрпример (вход, код, модель).
Ветки:
- E, а быстрого пути в коде ещё нет → сначала его пишет шаг 12 (быстрая ветка, проверка, `_x_reference`);
- E: стратегия на любой вход (откат) и стратегия на вход с инвариантом (быстрый путь);
- S: цепочки событий, зависимости подменены внутри `MonkeyPatch.context()`, `BaseException`, когда события кончились,
  взвешенные ветки, длины прогонов через `hypothesis.event`;
- C: часы фейкового хранилища подменены (1 мкс на команду), цепочки со всплесками на краях окон и нагрузочный тест
  на смоделированные сутки при реальных настройках;
- hypothesis идёт в тестовые зависимости репо (dev-группа uv, dev requirements, test extra или установка в CI);
  команда с `--no-project` - только для самостоятельного примера; без hypothesis тест падает, а не пропускается;
- нет lake → модуль оракула пропускается (`pytestmark`), CI нужен job с Lean.
Сбой: расхождение → показать до любой правки кода; решает пользователь, если не сказал заранее чинить; в режиме
карты код не меняется.
Module: `example/tests/test_spec_oracle`, `SKILL`

### 10. Известные находки (§5)

Решает: как известное расхождение остаётся на виду при зелёном гейте.
Ветки:
- A, E, режим карты: классификатор узких масок + один закреплённый контрпример на находку с `xfail(strict=True)`;
- S: без маски; пример из доказательства `¬ Claim` - закреплённый strict xfail, плюс тест, что код там равен модели.
Сбой: код починили → strict xfail падает → маску и пример убирают вместе.
Module: `references/known-findings`, `references/patterns`

### 11. Проверка мутациями (§5)

Решает: сравнивают ли тесты столько же, сколько теоремы.
Ветки:
- ≥3 поломки на шаблон (A: условие, сравнение, порядок; E: проверка, ключ, проверка инварианта; S: отметка
  «пробовали», повтор не того вида сбоя, запись на промежуточной попытке, не та цель, счётчик, флаг без сброса;
  C: сравнение с лимитом, починка срока жизни, сброс срока на каждый запрос, fail closed/open, пространство
  имён ключа; индекс или кэш: устаревшее состояние);
- выжившая поломка → тест сравнивает меньше теоремы → чинить тест;
- индекс или кэш в быстром пути → входы-почти-копии и `@example` на каждую пойманную поломку;
- эквивалентная поломка (меняет только ветку, не результат) → называется в отчёте.
После каждой правки маски проверка повторяется; каждая поломка откатывается через `cp` + `cmp`.
Module: `SKILL`

### 12. Быстрый путь и замер (§6, только E)

Решает: что работает в проде и быстрее ли оно.
Ветки:
- инвариант данных → проверка там, где инвариант может сломаться (на вызов, при старте + на запись); откат = эталон;
- свойство правила → без проверки, тест свойства; без гипотезы → проверять нечего;
- старый код остаётся как `_x_reference` для тестов.
Замер: медиана и p95, разогрев, GC выключен, одни и те же входы, реальные размеры + один больше + малый размер;
«до» - с шага 1, «после» - здесь.
Module: `SKILL`, `references/patterns`

### 13. Гейт (§7)

Решает: готово или нет.
Порядок: `lake build` → grep (`sorry`, `native_decide`, `axiom`, `implemented_by`, `extern`, `unsafe`,
`skipKernelTC`, `debug.`; без верхнего Frozen.lean и `.lake`) → `comparator.json` называет ровно теоремы `Frozen.lean`,
и каждое замороженное определение, которое зовёт оракул, достижимо из них →
`lake comparator` → `TEST_CMD` из корня репо.
Ветки: `TEST_CMD` = команда тестов CI репо или весь `tests/`; исключения - комментарием в скрипте; job CI без lake
пропускает тесты оракула, поэтому зелёный CI - это гейт, только когда есть lean-job из `setup.md`.
Тонкости grep: целые слова по сырому тексту, поэтому слово в комментарии тоже роняет гейт (переформулировать);
список теорем читает атрибуты и модификаторы (`@[simp]`, `protected`); достижимость по именам, с запасом.
Сбой: любой этап → ненулевой код, нет `gate: ok`; гейт, Frozen и comparator.json ради зелёного не ослабляются.
Module: `SKILL`, `example/lean/gate`, `references/cheating`

### 14. Отчёт (§8)

Решает: что заявлено.
Выход: **Доказано:** каждая теорема из `comparator.json` одной фразой; **Только проверено:** совпадение с моделью (число примеров,
пойманные поломки) и всё вне модели; где проверка во время работы и что при её сбое; находки с номерами; для S и C -
модель сбоев (что включено, что нет); для C - таблица ёмкости при реальных настройках.
Сбой: без двух списков задача не сделана.
Module: `SKILL`

### 15. Запись в карту (§9, только режим карты)

Решает: что карта логики узнаёт из прогона.
Выход: строка `Proved:` в конце шага; тест карты проверяет, что путь существует; находки в план, на который
указывает Known gaps; пометка, что зеркалу нужна та же строка; один раз - правило того же коммита для шагов с
`Proved:` и строка в шапке о том, что проверяет тест карты.
Ветки: быстрый путь → `Proved:` говорит, что чему равно и при каком условии.
Сбой: строки карты под код не переписываются; неверная строка - это находка.
Module: `SKILL`, `references/map-mode`
