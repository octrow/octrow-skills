# lean-spec: план работы

Обновлено: 2026-11-02. Версия плагина: 0.2.0.

## Цель

Агент делает код **быстрым и правильным одновременно**, как lean-derive-hargup в $12-server challenge (280 тыс. пользователей на VPS за $12):
- каждое ускорение - теорема «быстро = эталон» (при инварианте или свойстве правила);
- проверка во время работы с откатом на эталон, где она дешёвая;
- замер до и после, иначе ускорения нет.

Проверка правильности и карта логики - фундамент. Цель - доказанная скорость.

Почему Lean, а не проза (OpenSpec, Spec Kit, Kiro и т. п.): модель - функция, она однозначна; теорема собирается, только если следует из модели; правка определения роняет зависимые доказательства. Проза эти места пропускает. Плагин закрывает два звена, которых Lean не видит: проза → Lean (цитата строки, утверждение человеком, заморозка) и Lean → код (дифф-тесты, позже генерация кода).

## Правила работы

- Сначала 1-2 прогона, разбор простых ошибок, потом масштаб. Массовых запусков вслепую нет.
- Перед каждым прогоном - бюджет в токенах, после - фактический расход.
- Тестируем на пет-проектах, в копии репо, пока результат не показан.
- Ускорение без цифр до и после не засчитывается.

## Дальше

### v0.3 - скорость с доказательством (продолжение)

- Второй прогон на цели из разведки: замер, профиль, быстрый путь, теорема, проверка, замер после. Один прогон, бюджет по результату разведки.
- **Планы запросов к БД** (как `feedPlan_eq` у hargup): таблицы - списки строк, SQL - функция над ними; «быстрый план = SQL-спека при инварианте данных»; проверка версии данных во время работы.
- `scripts/bench.py` в скилле: общий замер (медиана, p95, разогрев, GC off, несколько размеров) вместо разового скрипта в каждом прогоне.
- Готово, когда: эвал «ускорь, но докажи» даёт ускорение по замеру, теорему и откат; ловушка «шорткат неверен при параллельной записи» ловится проверкой версии данных.

### Эвалы и харнесс (по ходу, когда мешает v0.3)

- Эвал-ловушка: агент тянется к `native_decide` или ослабляет формулировку - гейт падает, агент не обходит.
- Эвалы срабатывания скилла (`trigger-evals.json`).
- Прогон без плагина (базовая линия), когда эвалы стабильны. Сейчас `claude plugin eval` на этой машине не даёт агенту Bash, эвалы идут субагентом в копии фикстуры с ручной оценкой.
- Хуки: после правки `.lean` - проверка файла; Stop - `lean/gate.sh`. Проверить вживую.
- CI-шаг из `setup.md` прогнать на GitHub (bwrap на Ubuntu 24.04).
- Проверка формулировок вторым агентом без контекста доказательства; Plausible для поиска контрпримера до доказательства.

### v0.4 - Lean генерирует код (derive)

- Lean пишет часть прод-кода из спеки: константы, таблицы, готовые ответы, SQL-текст.
- Гейт: генерация, затем `git diff --exit-code` по сгенерированному файлу.
- Закрывает звено Lean → код точно, а не тестами.

### v0.5 - другие языки

Оракул не зависит от языка; меняется обвязка тестов.
- Go: rapid или fuzz; LeanPort для логики через cgo.
- Rust: proptest; Aeneas для доказательств о самом Rust-коде.
- TypeScript: fast-check; LemmaScript.

### OpenSpec как источник требований

`### Requirement` и `#### Scenario` ложатся на теоремы так же, как строки карты. Только для требований к логике.

### v0.6 - оркестрация

Субагент-прувер на одну `sorry`, эскалация в Aristotle, лимит попыток и времени, память о переименованиях API Lean.

### v1.0 - демонстрация

Реальный пет-проект: замер до, 1-3 доказанных ускорения с проверкой и откатом, замер после, разбор «что доказано / что проверено / сколько выиграли» с честным разделом «что не доказано».

## Риски

- Lean ломает API каждый месяц: пример и `proof-loop.md` проверяются на новой версии до её поддержки.
- Модель больше ~200 строк - режем цель.
- Неверная формулировка - главная дыра; до шорткатов с инвариантами нужна проверка формулировок вторым агентом.
- Ускорение там, где время уходит в сеть, пользователь не заметит: сначала замер всего запроса.
