# lean-spec: план работы

Обновлено: 2026-11-02. Версия плагина: 0.4.3. Карта логики скилла: `docs/logic-map.md`, находки: `docs/logic-map-fixes.md`.

## Цель

Агент делает код **быстрым и правильным одновременно**, как lean-derive-hargup в $12-server challenge (280 тыс. пользователей на VPS за $12):
- каждое ускорение - теорема «быстро = эталон» (при инварианте или свойстве правила);
- проверка во время работы с откатом на эталон, где она дешёвая;
- замер до и после, иначе ускорения нет.

Проверка правильности и карта логики - фундамент. Цель - доказанная скорость.

Скорость CPU - первый шаг, не граница. Lean должен держать **всю логику приложения**: протоколы и соединения, system design, GPU-ядра, IoT, конфигурацию и доступ. Везде одна схема: точная модель → теоремы → связь с реальной системой (тесты, оракул, проверка во время работы, генерация кода). См. раздел «Широта: вся логика приложения».

Почему Lean, а не проза (OpenSpec, Spec Kit, Kiro и т. п.): модель - функция, она однозначна; теорема собирается, только если следует из модели; правка определения роняет зависимые доказательства. Проза эти места пропускает. Плагин закрывает два звена, которых Lean не видит: проза → Lean (цитата строки, утверждение человеком, заморозка) и Lean → код (дифф-тесты, позже генерация кода).

## Правила работы

- Сначала низковисящие плоды (80/20): из открытых задач первой берём ту, что даёт больше всего пользы на единицу
  усилий (токены, размер модели, риск). Большие пилоты - после дешёвых правок, которые их страхуют.
- Сначала 1-2 прогона, разбор простых ошибок, потом масштаб. Массовых запусков вслепую нет.
- Перед каждым прогоном - бюджет в токенах, после - фактический расход.
- Тестируем на пет-проектах, в копии репо, пока результат не показан.
- Ускорение без цифр до и после не засчитывается.

Находки пилота S в jobs (код не менялся, ждут автора):
- **восстановление пакета на промежуточной попытке**: документация говорит «промежуточные попытки ничего не восстанавливают», а при `usage_limit` восстановление идёт на каждой попытке, потом повтор; контрпример: без провайдера, лимит, список [p0, p1];
- **пропуск живого провайдера**: вызов с заданным провайдером p1 упирается в лимит, роутер даёт [p2], первый повтор выкидывает голову списка, p2 никто не пробовал, прогон останавливается; правка: выкидывать голову только когда первая попытка была без провайдера.

Расход субагентов на всё это: около 2,2 млн токенов (пилот C - 238 тыс. при бюджете 150-250; правка находок jobs - 114 тыс. при 50-80; ревью карты - 102 тыс. при 60-90). До пилота C было около 1,64 млн токенов (прогон finance-insights - 123 тыс. при бюджете 150-250; пилот S - 156 тыс. при бюджете 180-280).

Находки пилота C в persona-crm (код не менялся, ждут автора):
- **LLM-ограничитель тоже пропускает всё при сбое Redis**: пока Redis лежит, украденный токен ничем не ограничен; это противоречит его же docstring («ограничивает ущерб от украденного токена»), а довод «fail open» в шапке модуля написан про вход, не про счёт за LLM. Решает автор: fail closed для LLM или запасной счётчик в памяти;
- две реплики могут продлить окно на задержку между INCR и EXPIRE (до 905 с вместо 900); лимиты от этого только строже, это не баг.

Уроки пилота C (внесены в скилл в 0.4.0 как шаблон C):
- модель, как в S, - функция переходов кода; время - число в событии, хранилище - значение;
- утверждения - границы счёта на отрезках времени; доказательство через «потенциал»: сколько ещё пропустят до момента b, шаг его не увеличивает, со временем он не растёт;
- учебные границы часто неверны на единицу или ложны (2L против 2L−1; L·(D/W+1)): все кандидаты сразу писать как `def Claim : Prop`;
- сбои - слагаемым «+ faultsIn» в самой границе, а не гипотезой «без сбоев»: сильнее и бесплатно;
- чередование реплик - отдельная маленькая модель на уровне операций; ложное утверждение закрепляется на реальном коде через asyncio-события;
- цифры ёмкости - следствия через `decide` при реальных настройках; таблица ёмкости - отдельный формат отчёта шаблона C;
- system-design дал мало: napkin.py считает DAU → серверы; полезна только рамка «отказанный запрос всё равно стоит INCR+TTL»;
- тесты: управлять часами фейка (fakeredis: подменить модульный `time`, плюс 1 мкс на команду), иначе граница c+W расходится; нагрузочный тест на сутки ловит поломки, которые короткие цепочки Hypothesis пропускают;
- гейт: если общая фикстура conftest требует Postgres, временный кластер в копии без Unix-сокета (длинный путь) и `TEST_DATABASE_URL`; это надо описать в setup.md;
- Lean 4.35: omega видит `L * cdiv x W` атомом, нормализовать вычитания (`Nat.sub_sub`); `Decidable` для своего `Sorted` - `unfold` перед `decide`; `pkill -f` убивает собственный шелл, брать `pgrep -f "[p]attern"`.

Уроки пилота S (внесены в скилл в 0.3.0 как шаблон S):
- модель - функция переходов кода, требования - утверждения документации: `def Claim : Prop` и `theorem claim_false : ¬ Claim` с конкретным свидетелем; без `sorry`, свидетель становится закреплённым xfail;
- окружение - один конечный список событий (исход попытки + ответ роутера), рекурсия структурная, граница числа попыток - теорема, а не топливо;
- `fun_induction step`, пары «попытка i - событие i» через `attempts.dropLast.zip evs`, граница через `List.Nodup.length_le_of_subset`;
- Lean 4.35: `match` в замороженной формулировке и такой же `match` в лемме выше - общий вспомогательный matcher, `lake comparator` пишет «statement do not match»; леммы без `match`; `List.dropLast_cons₂` устарел;
- Hypothesis: `st.one_of` тянет к простым веткам (80% вызовов с одной попыткой), веса через `st.integers(0, 9).flatmap`, распределение через `hypothesis.event`; `MonkeyPatch.context()` внутри `@given`; подменять и вспомогательные функции, которые снова зовут окружение.

Уроки прогона finance-insights (внесены в скилл в 0.2.1):
- шаблон E без гипотезы, когда ключ корзины - часть самого условия; шаг 6 не должен требовать проверку;
- приём доказательства «выдать и отсортировать, чтобы совпал порядок цикла»: пары как `(min, max)`, генератор даёт те же пары при любом порядке строк, затем `Perm.eq_of_pairwise`;
- `matches` - ключевое слово Lean; остаток `if false = true` закрывается `Bool.false_eq_true, ↓reduceIte`; у `bne_comm` неявные аргументы;
- в `example/tests/test_spec_oracle.py` нет пропуска без lake, хотя SKILL.md о нём говорит;
- агенту: рабочая папка сбрасывается между вызовами шелла, всегда абсолютные пути (агент один раз записал файлы не в тот репо и сам убрал);
- мутация «сравнивать банки по имени» ловится только картой, где два банка делят счёт: стратегии должны покрывать такие отображения.

### Широта: вся логика приложения

Lean доказывает свойства модели. Железо, сеть и время он не видит, поэтому в каждой области модель включает то, что может пойти не так (потеря сообщения, повтор, сбой узла, переполнение), а связь с реальностью держат тесты против оракула, симуляция или проверка во время работы.

| Область | Что моделируем | Какие теоремы | Связь с реальной системой | Есть ли пример | Сложность |
|---|---|---|---|---|---|
| Соединения и протоколы | конечный автомат соединения: состояния, события, таймауты, повторы | безопасность (никогда не шлём после close, не теряем подтверждённое), повторы + идемпотентность = эффект ровно один раз | дифф-тесты: случайные последовательности событий против оракула; лог событий из прода как вход | Veil (распределённые протоколы, CAV 2025) | средняя |
| System design | очереди, лимиты, ретраи, кэш, репликация как модели состояний и чисел | «кэш никогда не отдаёт значение старше TTL», «очередь не теряет при нагрузке ≤ ёмкости», «ретрай с ключом идемпотентности не дублирует платёж», согласованность чтения после записи | связка с плагином system-design: его цифры (RPS, ёмкость) - параметры теорем; нагрузочный тест против модели | AWS: TLA+ для сервисов; Lean - Veil | средняя-высокая |
| Доступ и конфигурация | правила доступа, политики, firewall, лимиты | «не владелец не видит чужой объект», «правило A не перекрывает B», нет противоречивых правил | дифф-тесты движка политик против модели | AWS Cedar (Lean + дифф-тесты) | низкая-средняя |
| GPU и численные ядра | наивное ядро как эталон (свёртка, редукция, матричное умножение), быстрое - тайлинг, слияние, другой порядок | быстрое ядро = наивное на целых или точных дробях; для float - граница ошибки | оракул на CPU сравнивает выход ядра с эталоном на случайных тензорах, с допуском, выведенным из теоремы | TorchLean (спецификации нейросетей в Lean) | высокая |
| IoT и встраиваемое | автомат устройства, калибровка, расписание опроса, буферы | автомат не застревает, буфер не переполняется при частоте ≤ N, калиброванное значение в пределах | симуляция с шумом датчика против модели; проверка диапазона на устройстве | LNSym (машинный код Arm) - для низкого уровня | средняя |
| Данные и миграции | схема, миграция, инварианты данных | миграция сохраняет инварианты, обратимость, нет потерь строк | прогон миграции на копии и сверка инвариантов | - | низкая-средняя |

**Новые шаблоны для скилла** (рядом с A и E):
- **S - автомат состояний.** Модель событий и состояний с моделью сбоев; теоремы безопасности по всем последовательностям событий; дифф-тесты на случайных последовательностях и на логе из прода.
- **N - численное ядро.** Эталон в точной арифметике, быстрое ядро, теорема равенства или граница ошибки; оракул с допуском из теоремы.
- **C - ёмкость и лимиты.** Параметры из system-design (napkin.py), теоремы «не теряем / не превышаем при нагрузке ≤ X»; нагрузочный тест против модели.

**Порядок:** S сделан в 0.3.0, C сделан в 0.4.0 по пилоту на persona-crm (пилот S на jobs, цикл повторов; дальше - протокол соединения с реальным логом событий как входом). Сначала был S (соединения и протоколы): они есть почти в каждом пет-проекте (боты, сборщики с ретраями, синхронизация), и ошибки там дорогие и плохо ловятся обычными тестами. Затем C вместе с плагином system-design, затем N (GPU), затем IoT. На каждую область - один пилот в копии пет-проекта из `~/dev`, бюджет до и расход после.

Честно: Lean не докажет, что сеть или железо ведут себя как модель. Он докажет, что **логика правильна при всех сбоях, которые мы в модель включили**. Какие сбои включать - решение человека, и оно пишется в отчёт.

## Риски

- Lean ломает API каждый месяц: пример и `proof-loop.md` проверяются на новой версии до её поддержки.
- Модель больше ~200 строк - режем цель.
- Неверная формулировка - главная дыра; до шорткатов с инвариантами нужна проверка формулировок вторым агентом.
- Ускорение там, где время уходит в сеть, пользователь не заметит: сначала замер всего запроса.
